# Архитектура MVP

## Принципы

1. Код ребёнка выполняется только в изолированном предпросмотре (ADR 0001).
2. Сервер — единственный источник правды о правах, подписках, лимитах ИИ и пройденных уроках.
   Клиенту не доверяем.
3. О ребёнке собираем минимум данных: никнейм, прогресс, проекты. Ни фамилии, ни телефона,
   ни фотографии, ни точного возраста без необходимости.
4. ИИ подключается через адаптер и не имеет полномочий: он только предлагает изменения кода,
   которые сервер проверяет, а ребёнок принимает или отклоняет.
5. Минимальное решение, которое безопасно и расширяемо. Без микросервисов и очередей,
   пока они не нужны.

## Схема (целевая, к этапу 5)

```
Браузер
 ├─ Приложение (Next.js, основной домен)
 │   ├─ Маршрут, урок, редактор, консоль
 │   └─ iframe → Исполнитель (отдельный домен, только статика)
 └─ ↕ HTTPS
Сервер Next.js (Route Handlers / Server Actions)
 ├─ Авторизация, роли «родитель» и «ребёнок»
 ├─ Проекты и версии, прогресс, проверка заданий
 ├─ ИИ-шлюз: лимиты → AIProvider → проверка ответа → журнал расходов
 └─ PostgreSQL (размещение и провайдер — после проверки требований, см. RISKS.md)
```

## Предварительная модель данных (этап 5, не реализована)

```
parent_account   id, email, password_hash / внешний вход, created_at, consent_at
child_profile    id, parent_id → parent_account, nickname, created_at   (без ФИО и контактов)
project          id, child_id, lesson_slug?, title, created_at, updated_at
project_version  id, project_id, files_json, source ('child' | 'ai_accepted' | 'reset'), created_at
lesson_progress  child_id, lesson_slug, status, completed_at, verified_by_server, result_version_id → project_version
quiz_result      child_id, lesson_slug, correct_first_try, total, created_at
subscription     id, parent_id, plan, status, current_period_end, provider_ref
payment_event    provider_event_id (UNIQUE — защита от повторной обработки), payload_hash, processed_at
ai_usage         id, child_id, mode, tokens_in, tokens_out, cost_estimate, created_at  (без текста запроса)
```

Права проверяются на сервере на каждый запрос: проект принадлежит ребёнку, ребёнок — родителю
текущей сессии. Идентификатор владельца из запроса клиента не используется.

## ИИ-наставник (этап 4, не реализован)

```ts
interface AIProvider {
  complete(req: { system: string; messages: Msg[]; maxTokens: number; schema?: JsonSchema }): Promise<AIResult>;
}
```

Процесс: запрос ребёнка → проверка лимитов и прав → минимальный контекст (текущие файлы урока,
без личных данных) → ответ в заданном формате (объяснение + предлагаемые файлы) → серверная
проверка формата, размера и допустимости → показ изменений с подсветкой → «Применить» или
«Отклонить» → новая версия проекта. Педагогические правила задаются в системном промпте
и проверяются на тестовом наборе: сначала наводящий вопрос и объяснение, готовый код — по
явной просьбе и не для задания, которое проверяется.

Выбор провайдера — только после проверки доступности API для российского юрлица, условий
обработки данных несовершеннолетних, трансграничной передачи и цены (см. RISKS.md).

## План ближайших задач

1. Этап 2 (до пилота): исполнитель на отдельном домене, тесты в Safari/Firefox/мобильных.
2. Этап 3: серверное хранение прогресса появится только вместе с аккаунтами (этап 5).
   До этого — улучшение уроков по отзывам первых детей.
3. Этап 4: адаптер ИИ и один режим («Объяснить ошибку») с лимитами, затем остальные режимы.
4. Этап 5: аккаунты родителя и ребёнка, PostgreSQL, серверная проверка уроков, версии проектов.
